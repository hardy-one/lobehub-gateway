Upstream protocol v2 and its compatibility rules are described in `0.4.0.md`.

## Final behavior after the sync

- **Tool-result forwarding** (`POST /api/agent/tool-result`) follows upstream: the gateway clears `type` and serializes the whole `tool_result` message, so `executionTimeMs`, `state`, and `workRegistration` are forwarded alongside `content`, `error`, `success`, and `toolCallId`. No hand-picked field whitelist.
- **v1 WebSocket authentication (`GET /ws`)** follows upstream: a verified JWT authenticates immediately (`auth_success`), and ownership is rechecked when `/api/operations/init` establishes the owner; a mismatched pending owner is disconnected with `userId mismatch`.
- **Service-token authentication before init** keeps this repository's behavior: a socket that presents the shared `SERVICE_TOKEN` while the operation owner is not yet established stays pending, receives no messages, and is authenticated with `auth_success` only after `init`, bound to the initialized `userId`. JWT-first and `apiKey` flows are unaffected.
- The excluded platform surfaces are unchanged: no admin APIs, metrics, Durable Object storage or WebSocket hibernation, multi-instance coordination, geo reporting, or admin reporting.
